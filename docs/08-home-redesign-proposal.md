# 08 主页改造方案

- 文档定位：主页信息架构、视觉骨架与角色层的改造提案
- 前置阅读：`emmo-style-reference.md`、`03-design-system.md`
- 状态：**待确认**
- 可视稿：`design/home-proposal.html`（含方案与现有结构的对照）

---

## 1. 现状的问题

对照稿见 `docs/design/home-proposal.png` 右侧。

**问题一：纵向列表，不可扫视。**

12 个工具排成一列，每个占约 110px 高，总长超过一屏半。工具之间是顺序关系，
用户需要逐条读下来才能找到目标。而工具集合本质是**并行**的，适合网格而非列表。

**问题二：单张卡片上叠了五层文字。**

以「二叉树可视化」为例，一张卡片上依次是：

| 层 | 内容 |
| --- | --- |
| 1 | 标题「二叉树可视化」 |
| 2 | 徽章「USELESS」 |
| 3 | 描述「输入层序遍历数组，自动生成可视化二叉树，支持保存为图片」 |
| 4 | 标签「算法」「工具」 |
| 5 | 日期「01-03」 |

其中描述平均 25 至 40 字，占据卡片一半面积。但这些描述的信息价值很低——
「二叉树可视化」这种标题本身已经说明了工具做什么，描述只是把标题换个说法
再讲一遍。

**问题三：图标没有视觉分量。**

图标容器 48px、图标本身 26px，在整张卡片中占比很小。工具的身份识别
完全依赖文字，视觉上是一片相似的白色卡片。

**问题四：缺少品牌表达。**

全站是「白卡片 + 文字」，没有任何情绪化的视觉元素。这与参照对象的
「温柔的陪伴」定位相去甚远。

## 2. 改造的三个层面

### 2.1 信息架构

| 项 | 现状 | 方案 |
| --- | --- | --- |
| 布局 | 单列纵向列表 | **两列网格** |
| 分组 | 无 | 按分类分组，组标题在卡片外 |
| 卡片内容 | 标题 + 徽章 + 描述 + 标签 + 日期 | **仅角色 + 标题** |
| 筛选 | 顶部标签胶囊行 | 分段控件（分段控件更紧凑，且与筛选语义匹配） |
| 页头 | 标题 + 副标题 + 主题按钮 | Logo + 圆形图标按钮组 |
| 主视觉 | 无 | 顶部角色 + 一句话简介 |

**卡片的文字削减是本次改动最核心的一条。** 从五层减到一层，靠角色形状
与颜色承担识别，标题只做确认。

被移除的信息去向：

| 信息 | 处置 |
| --- | --- |
| 描述 | 移除。标题已足够说明；确需补充时放到工具页内 |
| 标签 | 移除。已由分组标题表达 |
| 日期 | 移除。对使用者无价值，它是维护者视角的数据 |
| 徽章 | 移除。同理，且「USELESS」「IDK」这类文字对新用户是噪音 |

### 2.2 视觉骨架

| 元素 | 现状 | 方案 | 依据 |
| --- | --- | --- | --- |
| 卡片圆角 | 20px | 24px | 参照对象 App 卡片约 20 至 28px |
| 卡片阴影 | `elev-1` | `elev-1`，保持 | 参照对象用极淡阴影 |
| 底部导航 | 贴边通栏 | **悬浮圆角条 + 毛玻璃** | 参照对象 App 全部采用悬浮式 |
| 页头按钮 | 单个方形 | 圆形图标按钮组 | 参照对象的圆形白底按钮 |
| 筛选 | 描边胶囊 | 分段控件（灰底 + 白色浮动选中块） | 参照对象的 segmented control |
| 分组标题 | 无 | 灰字，置于卡片外 | 参照对象设置页的范式 |

### 2.3 角色层（新增）

**这是本次改动中工程量最大、也最能拉开与现状差距的一项。**

参照对象的品牌识别几乎全部由手绘角色承载：产品图标、装饰条、空状态、
导航中央按钮。本项目完全没有对应物。

#### 2.3.1 与现有图标体系的分工

现有 41 枚几何描边图标（24×24 栅格、`stroke-width 1.75`）**保留不动**，
继续承担界面功能：导航、按钮、状态指示。

角色层是另一套语言，只承担品牌表达：

| 层级 | 用途 | 画幅 | 风格 |
| --- | --- | --- | --- |
| 几何图标 | 界面功能 | 24×24 | 描边、单色、克制 |
| 角色 blob | 工具身份、主视觉、空状态 | 300×300 | 手绘、实心、粗描边 |

两套并存不冲突——参照对象自己也是这么做的（App 内大量使用系统风格的
线性图标，只在品牌表达处用角色）。

#### 2.3.2 三条绘制技法

来自 `smile.svg` 的源码分析（见 `emmo-style-reference.md` §3.2）：

**技法一：描边用同色系深色或粗黑。**
参照对象的 App 图标用粗黑描边（在小组件中保证辨识度），网站装饰角色
用同色系深色（更柔和）。本项目取**粗黑**，因为角色要出现在 64px 的卡片上。

**技法二：表情必须不对称。**
一只眼睛是小圆点，另一只是倾斜豆形，且大小差异明显。完全对称会呆板。
嘴巴为紧凑弧线，不用宽扁的笑脸。

**技法三：眼神光制造生气。**
在黑色眼睛上叠一个主体色小点。这是「可爱」感的关键来源，成本极低。

外加：腮红用低透明度暖色椭圆，进一步增加亲和力。

#### 2.3.3 形状体系

参照对象的产品图标各有专属轮廓：日记是圆润 blob、微笑 todo 是花瓣形、
Golite 是锥形。形状承载产品语义，颜色只做区分。

本项目的 12 个工具拟采用 4 种基础轮廓轮换：

| 轮廓 | 语义倾向 | 适用工具举例 |
| --- | --- | --- |
| 圆润型 | 温和、通用 | 二叉树、电子包浆 |
| 高瘦型 | 挺拔、结构 | 排序算法、图片像素化 |
| 花瓣型 | 发散、多彩 | 路径寻找、图片混淆 |
| 方块型 | 规整、秩序 | 字体转换、转 ASCII |

**待定：颜色的分配方式。** 三个选项：

| 方案 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 每个工具一色 | 12 个工具各用不同主题色 | 识别度最高 | 页面花，12 种颜色易失控 |
| B. 按分类配色 | 同一分类的角色同色 | 有分组感，颜色可控 | 同组内靠形状区分，识别较慢 |
| C. 全部随主题色 | 所有角色跟随当前 accent 色板 | 最克制，与主题系统天然联动 | 完全失去个体识别 |

可视稿采用 **B**（分类配色），因为它与「按分类分组」的信息架构一致。

#### 2.3.4 与主题系统的联动

角色主色取自当前 `--accent`，描边固定为深色。这样切换主题色板时角色
自动跟随，无需额外维护。

渐变主题（参照对象有 4 套渐变主题）需要角色支持渐变填充，属于
后续工作，本次不涉及。

## 6. 风险

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 角色绘制质量 | 手绘质感依赖路径控制点，机械化生成容易变成「几何图形加脸」 | 已出草稿验证，可读性达标；12 个形状需逐个调 |
| 颜色失控 | 12 种颜色同屏可能嘈杂 | 采用按分类配色（H2-B），同屏最多 4 色 |
| 信息丢失 | 移除描述后，工具用途可能不够明确 | 部分标题确实较泛（如「排序算法」），可在工具页内补说明 |
| 与既有图标体系割裂 | 两套视觉语言并存 | 明确分工：几何图标管功能，角色管品牌；参照对象亦如此 |

## 7. 修订：改为植物体系与货架结构

2026-09-18 修订。原方案的角色 blob（带脸）方向被否决，改为两条新方向。

### 7.1 角色层改为植物体系

**否决理由**：脸型体系与要表达的内容无关，且 12 个「圆脸」的区分度不足。

**新方向**：使用植物形态——叶片、蕨叶、花瓣、芽、莲座、藤蔓等。

| 维度 | 原（脸型） | 新（植物） |
| --- | --- | --- |
| 形态来源 | 不规则 blob + 五官 | 植物轮廓 |
| 区分手段 | 轮廓形状 + 颜色 | **物种形态**，天然差异大 |
| 笔法 | 粗描边 + 手绘 | 保持同一套笔法 |
| 花器 | 无 | **花盆**，作为统一的视觉锚点 |

植物体系的一个实际优势：**物种之间的形态差异远大于 blob 之间的差异**。
蕨叶、花瓣、莲座不会混淆，而 12 个圆 blob 需要靠颜色才能区分。

花盆的引入解决了另一个问题：脸型体系靠「脸」把所有元素统一起来，
去掉脸之后需要一个替代的统一元素——**花盆承担了这个角色**。

色相上拉开层次，避免「一片绿」：深青绿、黄绿、粉、嫩黄绿、蓝灰绿、橄榄。

### 7.2 主页改为货架结构

**否决理由**：卡片网格仍是「标准结构化」排列，且卡片本身就是最常见的形态。

**新方向**：不用卡片，改用**货架**——植物连盆坐在木板上，标签贴在板沿下方。

```
   算法                       ← 分组标题
   🌿   🌱    🌿              ← 植物高低错落，非等距
  ══════════════════════     ← 木板（三层叠加做出厚度）
   二叉树  排序   路径         ← 标签，与植物用 grid 严格对齐
```

**「非标准化」体现在三处**：

| 维度 | 处理 |
| --- | --- |
| 尺寸 | 每株高度不同（4 档：44/52/60/48 px 宽） |
| 位置 | 同一货架上不等距，由植物宽度自然形成疏密 |
| 形态 | 物种不同，轮廓各异 |

**货架与分类的对应**：一层货架 = 一个分类。分组由结构本身表达，
不再需要额外的分组标题样式——标题就写在货架上方。

**布局要点**（实施时必须遵守，可视稿中踩过）：
标签不能放在花盆下方，会被木板遮挡。正确结构是三层分离：
植物 → 木板 → 标签，且两层用同一套 `grid-template-columns` 保证对齐；
用 `flex: space-around` 会因各植物宽度不同而错位。

### 8.2 植物形态的修复

审阅发现的形态问题与修法：

| 形态 | 原问题 | 修法 |
| --- | --- | --- |
| 蕨 | 两枝交叉成 X，叶片出界被裁（左 x=-2、右 x=82） | 改为单枝拱形羽叶，叶片沿茎两侧交替并递减 |
| 花 | 花瓣出界（x=-2），整朵过大，盆被迫缩小 | 花瓣外移收窄；花心加大以盖住瓣根 |
| 花（二次） | 五瓣在中心重叠，粗描边把粉色糊成一团黑 | 花瓣基部下移、加大中心留白，让填充色露出 |
| 莲座 | 读作同心椭圆（洋葱/蛋） | 改为尖叶放射，外层摊开内层立起 |
| 藤蔓 | 斜生枝条，有一片叶长在盆沿外 | 改为拱形攀藤 |
| 藤蔓（二次） | 与蕨叶形状过近，难以区分 | 改用**圆叶**，与蕨的尖细羽叶形成对比 |
| 阔叶 | 茎插入盆内，叶柄生出多余叉枝 | 改用「基准叶 + 旋转」构造，几何可预测 |

**根因**：初版手工计算贝塞尔控制点，没有约束在 80×120 的 viewBox 内，
导致多处出界被裁。改用的做法是——

**先定义一片标准叶（基部在盆口、尖端到顶），再用 `transform: rotate`
绕基部复制。** 旋转半径恒定，几何可预测，不会出界，且各方向叶片
自然对称。此法已用于阔叶与花。
