## 各文档核心结论速览

### 01 结构重构方案

- **目标分层**：`app/`（装配）、`design/`（设计系统）、`shared/`（跨模块共享）、`modules/`（业务模块）
- **数据源统一**：以每个工具的 `manifest.ts` 自声明取代中心文件罗列，消除 `PagesData.ts` / `navItems.json` / `tags.js` 三写
- **雪藏 lessonTable**：整体移入**仓库根目录**的 `archive/`，而非 `public/archive/`——后者会被 Vite 打进构建产物，导致个人课表数据随应用发布
- **清理量**：22 个 0 字节占位文件、2 个空目录、2 项死代码、1 项重复实现

### 02 融合架构方案

- **为什么必须弃用 iframe**：7 条理由中，**视觉无法统一是决定性的**——iframe 样式完全隔离，不融合就永远做不到风格统一
- **四阶段模型**：Stage 0 iframe 桥接 → Stage 1 模块归位 → Stage 2 逻辑提取 → Stage 3 视图重写 → Stage 4 旧目录下线
- **纪律**：Stage 1 必须纯搬运。若顺手改代码，出问题将无法区分是搬家搬坏还是改动引入
- **首迁目标**：`eft`（字体转换），风险最低，用作范式验证

### 03 设计系统规范

- **调性来源**：参照 emmo.club 旗下软件（EMMO 日记 / 小账本 / 手帐）的「清新、治愈、极简、手帐质感」方向
- **调研限制**：官网直接访问被环境策略拦截，风格依据来自公开渠道的文字描述归纳，具体色值为自拟方案，需你核对
- **核心变化**：弃用纯黑纯白，改用暖色纸感基底（`--paper-*`）与暖黑文字（`--ink-*`）
- **令牌三层**：原始令牌 → 语义令牌 → 组件引用。组件只允许引用语义层，这是主题切换生效的前提
- **马卡龙色板**：六套可切换主题色（玫瑰 / 蜜桃 / 奶油 / 薄荷 / 天青 / 丁香）
- **质感层**：纸纹与手绘描边是当前完全缺失的维度，也是拉开差距的关键

### 04 图标体系与去 emoji 方案

- **存量盘点**：107 种 emoji、518 处出现、35 个文件
- **实际工作量远小于此**：剔除未接入页面（约 300 处）、待删文件（约 47 处）、文档排版符号（约 40 处）后，核心迁移面约 60 处
- **发现的问题**：图片转 ASCII 与路径寻找可视化**共用了同一个 emoji**——这正是 emoji 图标数量不足的必然结果
- **双层级设计**：Tier 1 `line` 用于界面功能，Tier 2 `spot` 用于工具身份（对应 EMMO 的贴纸体系）
- **强制机制**：检测脚本接入 `build`，含 emoji 的代码无法产出构建

### 05 账户系统方案（待定）

- **最重要的产品决策**：**工具必须保持未登录可用**。账户是增量能力，不是准入门槛
- **推荐路线**：自建 Java 后端（Spring Boot 3 + PostgreSQL + Redis）为主，本地优先为基线
- **双令牌设计**：访问令牌短有效期（15 分钟，仅存内存）+ 刷新令牌可撤销（存哈希，带旋转与重用检测）
- **需你决策 8 项**：见下方台账

## 实施总路线

四份方案文档的执行顺序存在依赖，建议如下：

```
[阶段一] 结构与清理
    └─ 执行 01 的 §9 步骤 1-6
       （归档、雪藏、清死代码、建骨架、迁移、统一数据源）
            │
[阶段二] 视觉重塑
    └─ 执行 03 的 §10 与 04 的 §7
       （设计令牌、主题切换、图标体系、去 emoji 检测）
            │
[阶段三] 融合迁移
    └─ 执行 02 的 §8
       （13 个工具逐个从 iframe 迁为 native）
            │
[阶段四] 账户接入
    └─ 执行 05 的 §10
       （依赖阶段一的分层与阶段三的融合进度）
```

**阶段一与阶段二可部分并行**，但阶段三必须等阶段一完成（模块骨架就位），阶段四必须等阶段三推进到一定程度（否则账户只能覆盖外壳，工具内部无法接入同步）。
